# Codex 작업 로그 가이드

이 디렉터리는 Codex가 이 저장소에서 이슈 단위 작업을 수행할 때 남기는 한글 작업 로그와 설계 결정 기록을 보관한다.

## 목적

- 어떤 작업을 했는지 나중에 추적할 수 있게 한다.
- 왜 이런 구현을 선택했는지 설계 결정을 남긴다.
- PR 설명과 별개로 구현 과정의 판단 근거를 축적한다.
- 다음 작업자가 이어받을 수 있는 운영 문서 역할을 한다.

## 언제 작성해야 하는가

다음 중 하나에 해당하면 작업 로그를 작성한다.

- GitHub issue 기준으로 독립 작업을 시작할 때
- worktree 또는 전용 브랜치를 새로 만들어 작업할 때
- 설계 선택이나 범위 조정이 필요한 비단순 작업일 때
- PR 설명만으로는 맥락이 부족할 것으로 보일 때

단순 오타 수정, 주석 수정, 한 파일 내 소규모 기계적 변경은 생략할 수 있다.

## 파일 위치와 이름 규칙

- 위치: `docs/worklogs/`
- 파일명 형식: `YYYY-MM-DD_issue-<번호>_<slug>.md`

예시:

- `docs/worklogs/2026-03-30_issue-33_home-hero-hierarchy.md`
- `docs/worklogs/2026-03-30_issue-31_admin-sidebar-foundation.md`

하나의 이슈에 하나의 로그 파일을 기본으로 한다.
같은 이슈를 여러 차례 이어서 작업해도 가능하면 기존 파일에 누적 기록한다.

## 작성 원칙

- 한국어로 작성한다.
- 결과만 쓰지 말고 판단 근거를 쓴다.
- 장황한 회고보다 실제 구현과 결정 사항을 중심으로 쓴다.
- 코드 diff를 복붙하지 말고 변화의 의도를 요약한다.
- 미완료 항목과 리스크를 숨기지 않는다.

## 필수 섹션

아래 섹션은 비단순 작업에서 기본으로 포함한다.

1. `기본 정보`
2. `작업 목표`
3. `작업 내역`
4. `설계 결정 기록`
5. `검증`
6. `남은 이슈 / 후속 작업`

## 권장 템플릿

복사 시작:

```md
# 작업 로그: <작업명>

## 기본 정보
- 작성일: 2026-03-30
- GitHub Issue: #33
- 브랜치: `codex/ui-home-hero-hierarchy`
- 작업자: Codex

## 작업 목표
- 이번 작업에서 해결하려는 문제를 1~3줄로 정리한다.
- 범위 밖 항목이 있다면 함께 적는다.

## 작업 내역
### 1. 분석
- 어떤 파일과 흐름을 먼저 확인했는지 적는다.
- 기존 구현에서 확인한 핵심 문제를 적는다.

### 2. 구현
- 어떤 파일을 어떻게 수정했는지 요약한다.
- 단순 나열보다 기능 단위로 정리한다.

### 3. 범위 조정
- 원래 계획과 달라진 점이 있다면 적는다.
- 왜 범위를 줄이거나 넓혔는지 적는다.

## 설계 결정 기록
### 결정 1. <결정 제목>
- 배경: 왜 결정이 필요했는가
- 선택: 무엇을 채택했는가
- 이유: 왜 이 선택이 가장 적절했는가
- 대안: 검토했지만 채택하지 않은 방법
- 영향: 이후 작업이나 구조에 미치는 영향

## 검증
- 실행한 테스트:
- 수동 확인:
- 확인하지 못한 항목:

## 남은 이슈 / 후속 작업
- 아직 남은 리스크나 개선 포인트를 적는다.
- 다음 PR 또는 다음 이슈로 넘길 항목을 적는다.
```

복사 끝.

## Work Status 와의 연결 규칙

GitHub issue 본문에 `Work Status` 체크리스트가 있다면 다음 기준을 따른다.

- 브랜치 또는 worktree를 만들고 구현을 시작하면 `진행 중`으로 바꾼다.
- 구현, 검증, 로그 정리가 끝나 리뷰 가능한 상태가 되면 `진행 완료`로 바꾼다.
- 멈춘 작업은 `진행 중` 상태를 유지하되, 로그의 `남은 이슈 / 후속 작업`에 현재 상태를 명확히 적는다.

## 좋은 예시

- "홈 hero의 우측 정보 패널이 첫 화면의 주 메시지를 압도해서, 통계/최근 글 블록을 다음 섹션으로 이동했다."
- "관리자 셸은 기존 커스텀 sidebar를 유지하면 페이지별 편차가 커질 수 있어 shadcn sidebar primitive로 구조를 통일했다."
- "폼 색상 override가 여러 파일에 흩어져 있어 button/badge/input variant 쪽으로 흡수하는 방향을 택했다."

## 피해야 할 예시

- "많은 파일을 수정했다."
- "버그를 고쳤다."
- "적당히 리팩토링했다."

이 수준의 문장은 결과는 말하지만 판단 근거와 구현 방향을 남기지 못한다.
